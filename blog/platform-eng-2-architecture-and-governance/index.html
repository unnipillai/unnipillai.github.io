From Vision to Internals

Most platform engineering efforts die in the architecture phase. The technology is usually fine. What’s missing is a clear answer to who owns what, who’s on call, and how governance works without turning into a bottleneck.

Part 1 covered why platform engineering matters. This part goes inside the platform and covers three things:

1/ The 5-layer architecture: what each layer does and how the layers fit together.

2/ The operating model: who owns what, who’s on call, and how the platform team works as a product team.

3/ Governance-as-code: how to build compliance in without creating bottlenecks.

1. The 5-Layer Platform Architecture

The platform is modular and easy to extend, and every interface behaves the same way because every capability goes through the same API, whether your developers use the CLI, the UI or the API directly.

Layer 1: Developer Interface

This is the surface your developers work with: three interfaces on top of one API.

  • API Gateway is the primary surface. All capabilities are exposed through versioned APIs, which is what keeps the other interfaces consistent.
  • CLI Tool is for power users and CI/CD integrations. Think dip create, dip deploy, dip monitor. It uses the same API as everything else.
  • UI Portal covers visual workflows, service discovery, scaffolding and dashboards. It works well for onboarding and for browsing services.

The guiding principle is that every capability is available through the API, the CLI and the UI.

Layer 2: Platform Core Services

Most of the platform’s logic sits here.

  • Service Blueprint Engine provides golden templates for common service types. A developer says “I need a REST API service” and gets a fully scaffolded project with CI/CD, logging, tracing and compliance hooks already wired in.
  • Infrastructure Blueprint Engine manages reusable, versioned modules for provisioning infrastructure. Databases, queues, caches and storage are all defined as curated blueprints that hide the cloud-specific details.
  • Pipeline Orchestrator standardizes CI/CD pipelines across teams, using shared templates with hooks for security scanning, policy checks and automated testing.

Layer 3: Policy & Compliance

This is the layer where governance becomes part of the platform itself.

  • Policy-as-Code Engine uses OPA (Open Policy Agent) or a similar tool to evaluate policy at runtime. Rules like “all storage must be encrypted at rest” or “no public-facing resources without TLS” are checked automatically during provisioning and deployment.
  • Input Validators catch bad requests early. Before a blueprint runs, its parameters are checked against schemas, allowed values and organizational constraints.
  • Security Scanners are embedded in every pipeline. SAST, container scanning and IaC scanning all run automatically as part of the golden path.

Layer 4: Provisioning & Runtime

This layer carries out the actual infrastructure and service deployments.

  • Infra Provisioning Controller manages the infrastructure lifecycle through Terraform, Crossplane or Pulumi, covering creation, updates, drift detection and teardown.
  • Service Deployment Controller integrates with GitOps tools (ArgoCD, Flux) or CI/CD runners to deploy applications across environments.
  • Environment Orchestrator handles multi-environment support, cloud-region mapping and on-prem orchestration. Developers spin up environments through the platform, and this layer deals with the complexity underneath.

Layer 5: Observability & Audit

Every service deployed through the platform comes with observability already configured.

  • Telemetry Hooks bake logging, metrics and tracing into the blueprints through OpenTelemetry, Prometheus and Grafana, so developers never have to set up monitoring themselves.
  • Audit Trail Collector logs every action taken through the platform: who provisioned what, when and from where. You need that for compliance and for debugging.
  • Cost & Usage Monitor auto-tags resources and links them to cost dashboards, so teams see their spend as it happens instead of at the end of the quarter.

2. The Operating Model

The architecture only works if people know how to operate inside it, and this is where “you build it, you run it” either holds up or falls apart.

Role-Based Ownership

RoleResponsibilitiesOwns
Developer TeamsBuild, deploy, and operate services end-to-end. Consume platform APIs, templates, and pipelines. Define SLOs, monitor performance, manage incidentsService code, infra blueprints used by their service, alerts, dashboards
Platform Engineering TeamBuild and maintain the internal developer platform. Curate and version blueprints. Own API, CLI, and UI layers. Implement policy-as-code. Maintain developer docs and onboardingPlatform core, shared templates, policy bundles, governance tooling
Security & RiskDefine compliance, security, and data protection policies. Review and audit policy bundles with platform teamRegulatory inputs, escalation triggers, risk scoring logic
SRE (Optional / Embedded)Guide dev teams in adopting SLOs and resilience patterns. Help establish observability standards. Coach teams through incident reviewsReliability practices, SLO/SLI models, observability standards

A common mistake is to treat the platform team as an operations team. It doesn’t run your services or provision infrastructure for your teams. It builds and maintains the platform that lets everyone else do those things on their own. Get this distinction wrong, and you’ve just renamed your ops team.

On-Call & Incident Ownership

LayerOn-Call OwnerNotes
App / Service RuntimeDeveloper teamAlerts configured via platform, tied to service-level SLOs
Blueprint / Platform IssuesPlatform teamBugs in templates, deploy flow, policy logic, API failures
Infra FailuresPlatform team (initial), cloud escalation if neededProvisioning failures, limits, misconfiguration
Security IncidentsSecurity team, with dev team coordinationAlerts from scanning, policies, or external events

When something breaks at 2am, the team that built the service handles the first response. The platform team takes the platform-level issues: blueprint bugs, provisioning failures and policy engine outages.

Proactive Support Model

“You build it, you run it” doesn’t mean “you’re on your own.” The platform team backs it up with:

  • Office hours, regular sessions for onboarding and problem-solving
  • Support channels such as #ask-platform, #policy-help and #blueprint-feedback
  • Embedded champions, platform team members who sit with key product squads for a while during early adoption

Platform as Product: Ways of Working

The platform team works like a product team rather than a service desk. In practice that looks like this:

PracticeHow It’s Done
Customer DiscoveryBiweekly feedback sessions with dev teams, friction log reviews
Backlog ManagementKanban or dual-track agile: prioritized by adoption, internal demand, and risk
Release ManagementVersioned blueprint releases, changelogs, backwards compatibility guarantees
Adoption MetricsTrack services onboarded, time-to-deploy, pipeline usage, developer satisfaction
DocumentationFirst-class artifact: built into CLI/UI flows and auto-generated from blueprints

3. Governance-as-Code

In a regulated industry (fintech, banking, insurance), governance is mandatory, but it shouldn’t become a bottleneck. I’ve seen organizations where a compliance review adds two weeks to every deployment. At that point it has stopped being governance and turned into a queue.

The platform uses a governance-as-code model that enforces security, compliance and best practices automatically at several layers. Developers move fast inside safe guardrails, security teams get assurance and auditors get their logs, with no manual gates in the way.

Three Enforcement Layers

LayerDescriptionTools / Methods
Input ValidationParameters validated before infra or service creationJSON schema, regex, CLI validators, UI constraints
Policy-as-CodeDynamic rules evaluated during blueprint execution and deploymentOPA / Gatekeeper, Conftest
Pipeline HooksAll CI/CD pipelines include required scanning and loggingSnyk, Trivy, Checkov, custom admission controllers

Policy Bundle Design

Policies are organized as modular bundles and managed like application code: versioned, tested, and deployed with changelogs.

Governance Lifecycle

StepDescription
AuthoringPlatform team and security team collaborate to define policy logic
TestingPolicies tested against sandbox blueprints and sample inputs
ReleasingVersioned and rolled out via changelog and flagging system
MonitoringViolations logged with dashboards showing policy hits/failures
ReviewingPeriodically audited and reviewed with stakeholders
